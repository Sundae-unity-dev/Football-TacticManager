# 성능

**재 보기 전에는 아무도 몰라요.** 그래서 이 문서의 숫자는 전부 직접 잰 것이고, 어디서 쟀는지도 같이 적어 뒀어요.
데스크톱과 브라우저는 3배, 개발 서버와 배포본은 17배나 차이가 나거든요.

먼저 저장 한 번이 지나가는 길과, 하나하나 쪼개 재서 알게 된 비용이에요.

```mermaid
flowchart LR
  W["GameWorld<br/>선수 6,000 · 구단 240"] -->|"JSON 108ms"| J["2.73MB"]
  J -->|"gzip 62ms"| G["610KB"]
  G -->|"base64 1ms"| S["브라우저 저장<br/>813KB"]
```

선수 한 명을 객체 대신 **숫자 배열 하나로 접어서** 이 길의 첫 칸에서 390ms 를 덜어 냈어요.
어떻게 찾아냈는지는 아래 "세이브를 쪼개 보고 선수를 접었어요"에 적어 뒀어요.

## 세계 규모

> 이 표는 가상 4개국으로 세계를 만들던 때(v0.12 이전) 잰 값이에요. 지금은 실제 나라 중에서 고르지만,
> 기본 크기(구단 240 · 선수 6,000)는 같아서 비용도 비슷한 자리에 있어요.

| | |
|---|---|
| 국가 | 4 (노르셀 · 벨마라 · 할브룬 · 소란) |
| 리그 | 12 (나라마다 1~3부, 각 20팀) |
| 구단 · 선수 | 240 · 6,000 |
| 시즌당 리그 경기 | 4,560 |
| 컵 | 나라마다 국내 컵 60팀 + 대륙 챔피언스컵(4개조 16팀 → 8강) |
| 세계 생성 | **102ms** (릴리스·차가운 상태 = 새 게임을 시작할 때 겪는 값) · 44ms (데워진 뒤) |
| 라운드 한 회 | **7~8ms** (릴리스·데워진 뒤 — 리그 경기 3.2 · 주간 진행 4.5) |
| 〃 | 20ms (디버그) · 첫 회 27ms (계층 컴파일이 올라오기 전) |
| 시즌 넘김 | 97ms (릴리스) |
| 세이브 | 610KB (원본 2.73MB 를 gzip) · 쓰기 90ms · 읽기 130ms (데워진 뒤) |
| 〃 | 첫 저장만 360ms 예요 — JSON 직렬화가 처음 도는 값이고, 압축은 늘 50ms 로 같아요 |

## 배포 빌드에서 잰 값 (2026-11-01)

위 수치는 전부 데스크톱(`FT.Sim`)에서 잰 거예요. 그런데 사람이 실제로 게임을 하는 곳은 브라우저잖아요.
그래서 `dotnet publish -c Release` 한 결과를 정적 서버에 올리고, 크롬에서 다시 쟀어요.

| | 데스크톱 | 배포 빌드(브라우저) |
|---|---|---|
| 세계 생성 | 102ms | **275ms** |
| 라운드 한 회 | 7.6ms | **73ms** |
| 저장 한 번 | 90ms | **175ms** (JSON 108 · gzip 62 · base64 1) |
| 세이브 읽기 + 첫 화면 | 130ms | **약 2초** (새로고침 → 저장된 판 복구까지) |

처음 내려받는 양은 **5.15MB**(brotli, 파일 41개 · 전체 요청 48개)예요. 압축하지 않으면 23.3MB 이고,
로컬에서 빈 캐시로 첫 화면까지 1.0초 걸려요. 처음 한 번만 받으면 그다음부터는 브라우저가 캐시해 둬요.

이 숫자는 **두 번 주고받기**를 해서 정해졌어요.

**트리밍을 켰어요 — 8.0MB → 2.8MB.** 예전 `FT.App.csproj` 는 "트리밍이 모델 타입을 지우면 세이브가 깨진다"는
이유로 트리밍을 꺼 뒀어요. 그런데 그 사이 `SaveGame.Options` 가 소스 생성 리졸버(`SaveJsonContext`)를 **먼저**
쓰도록 바뀌면서 그 걱정이 사라졌어요. 그래도 안전을 운에 맡기진 않으려고 `TrimmerRootAssembly` 로 모델 타입이
모여 있는 FT.Core 를 통째로 남겨 뒀어요. 남겨 둬도 크기는 거의 그대로예요(줄어드는 건 대부분 BCL 쪽이라서요).
덤으로 `SaveGame.cs` 의 IL2026 경고 다섯 개도 사라졌어요. 혹시 나중에 모델 타입을 FT.Core 밖으로 옮기게 되면
이 설정도 같이 옮겨 주세요.

**AOT 도 켰어요 — 2.8MB → 5.15MB 로 커지는 대신, CPU 는 3.7배 빨라져요.** 브라우저의 기본 런타임은 IL 을
해석하면서 돌아요. 이 게임은 저장 한 번에 멤버를 수십만 번 건드리니까 그 해석 비용이 고스란히 기다리는 시간이
돼요. 미리 컴파일해 두니 저장의 JSON 쓰기가 350 → 108ms, 라운드가 150 → 73ms 로 줄었어요.
한 번 받아 두고 몇 시간씩 하는 게임이라, 내려받는 양을 조금 양보하는 쪽을 골랐어요.

다만 `dotnet workload install wasm-tools` 가 있어야 하고, **배포 빌드가 40초에서 20분쯤으로** 길어져요.
CI 를 붙일 때 이 점은 꼭 기억해 두세요. 개발할 때(`dotnet run`)는 아무 영향이 없어요.

### 세이브를 쪼개 보고 선수를 접었어요 (2026-11-01)

배포본에서 저장 한 번에 560ms 가 걸렸어요. 쪼개 보니 답이 딱 하나로 나오더라고요.

```
JSON 490ms · gzip 70ms · base64 5ms
  └ 선수 6,000명  3,564KB  396ms   ← 전체의 81%
    구단   240개    574KB   89ms
    리그    12개    353KB   32ms
```

**사실 짐작은 두 번이나 빗나갔어요.** 처음엔 압축이 범인인 줄 알고 브라우저 기본 `CompressionStream` 으로
바꿀까 했는데, gzip 은 70ms 밖에 안 걸렸어요(네이티브 zlib 이라 이미 빨라요). base64 를 빼고 IndexedDB 에
바이트로 바로 넣을까도 했는데, base64 는 5ms 였어요. 그 둘을 고쳤다면 한나절을 쓰고도 하나도 못 줄였을 거예요.

선수 한 명이 594바이트였는데, 그중 **300바이트가 이름**이었어요. 능력치는 이미 배열이었지만 선수 자신은 객체라서
`"internationalGoals"` 같은 필드 이름 스물다섯 개를 6,000번씩 적고 있었던 거죠. 스태프를 접을 때 썼던 방법을
선수에게도 그대로 썼어요(`PlayerConverter`).

| | 전 | 후 | AOT 까지 켠 뒤 |
|---|---|---|---|
| 세이브 원본 | 4.48MB | **2.73MB** | 〃 |
| 압축 후 | 695KB | **610KB** | 〃 |
| 선수 한 명 | 594B | **321B** | 〃 |
| 전술 슬롯 하나 | 76B | **14B** | 〃 |
| JSON 쓰기(브라우저) | 490ms | **350ms** | **108ms** |

구단에서 제일 큰 건 저장된 전술이었어요(2,403B 중 1,227B). 그중 840B 가 슬롯 열한 개였고요.
슬롯 하나가 `{"slotIndex":1,"position":8,"role":{"role":8,"duty":1},"assignedPlayerId":17}` 인데,
정작 값은 숫자 다섯 개뿐이에요. 240구단 × 11자리면 이름만 180KB 나 돼요(`FormationSlotConverter`).

**중첩된 묶음은 변환기를 직접 불러 주세요.** 처음에는 능력치·계약·기록을 `JsonSerializer.Serialize` 로 다시
넘겼는데, 바이트는 46% 줄었는데 시간은 그대로였어요. 선수마다 아홉 번씩, 6,000명이면 54,000번이나 타입 정보를
새로 찾고 있었던 거예요. 변환기를 한 번 찾아서 들고 쓰니까 그제야 시간도 따라 내려왔어요.
**바이트가 준다고 시간까지 주는 건 아니더라고요.**

**뒤쪽의 0 은 적지 않아요.** `AttrJson.WriteArray` 가 꼬리에 붙은 0 을 잘라 내요. 한 경기도 안 뛴 선수의 시즌·통산
기록(열두 자리씩)과 아무도 건드리지 않는 계약 뒷부분이 6,000명분 쌓여 있었거든요. 읽는 쪽이 모자란 자리를 0 으로
채우니까 값은 똑같고, 예전 세이브도 그대로 읽혀요.

측정은 `/perf` 화면에서 해요. 메뉴에는 없어서 주소창에 직접 쳐야 들어갈 수 있어요.
저장을 세 번 재서 조각별로 쪼개 보여 줘요.

### 데스크톱 수치도, 개발 서버 수치도 배포본을 예측하지 못해요

`dotnet run` 개발 서버에서 재면 **저장 한 번이 3.0초**로 나와요. 같은 릴리스 코드인데 배포본에서는 0.175초예요.
열일곱 배 차이죠. 개발 서버는 디버깅을 켠 채로 돌아서 런타임 최적화가 빠지고, AOT 도 publish 할 때만 켜지거든요.
개발 서버에서 본 "3초"만 믿고 저장 코드를 뜯어고치려 들면, 있지도 않은 병목을 쫓게 돼요.
브라우저 수치는 **꼭 `publish` 한 결과로** 재 주세요.

재는 방법에도 함정이 하나 있어요. 확장 도구로 버튼을 누른 다음 **그다음 호출에서** 시간을 재면, 왕복 시간에 묻혀서
21ms 같은 엉뚱한 값이 나와요. 스크립트 한 번 안에서 `button.click()` 을 하고 `performance.now()` 차이를 봐야
제대로 나와요 — 무거운 일은 그 `click()` 안에서 동기로 끝나거든요.
