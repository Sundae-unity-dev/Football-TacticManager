# 성능

**재기 전에는 모릅니다.** 이 문서의 숫자는 전부 잰 것이고, 어디서 쟀는지를 같이 적습니다 —
데스크톱과 브라우저가 3배, 개발 서버와 배포본이 17배 차이 납니다.

저장 한 번이 지나가는 길과, 쪼개 재서 알게 된 비용입니다.

```mermaid
flowchart LR
  W["GameWorld<br/>선수 6,000 · 구단 240"] -->|"JSON 108ms"| J["2.73MB"]
  J -->|"gzip 62ms"| G["610KB"]
  G -->|"base64 1ms"| S["브라우저 저장<br/>813KB"]
```

선수 한 명을 객체가 아니라 **숫자 배열 하나로 접어서** 이 길의 첫 칸을 390ms 줄였습니다.
어떻게 알아냈는지는 아래 "세이브를 쪼개 보고 선수를 접었습니다"에 있습니다.

## 세계 규모

| | |
|---|---|
| 국가 | 4 (노르셀 · 벨마라 · 할브룬 · 소란) |
| 리그 | 12 (나라마다 1~3부, 각 20팀) |
| 구단 · 선수 | 240 · 6,000 |
| 시즌당 리그 경기 | 4,560 |
| 컵 | 나라마다 국내 컵 60팀 + 대륙 챔피언스컵(4개조 16팀 → 8강) |
| 세계 생성 | **102ms** (릴리스·차갑게 = 새 게임에서 겪는 값) · 44ms (데워진 뒤) |
| 라운드 한 회 | **7~8ms** (릴리스·데워진 뒤 — 리그 경기 3.2 · 주간 진행 4.5) |
| 〃 | 20ms (디버그) · 첫 회 27ms (계층 컴파일이 올라오기 전) |
| 시즌 넘김 | 97ms (릴리스) |
| 세이브 | 610KB (원본 2.73MB gzip) · 쓰기 90ms · 읽기 130ms (데워진 뒤) |
| 〃 | 첫 저장은 360ms — JSON 직렬화가 처음 도는 값이고, 압축은 50ms 로 늘 같다 |

## 배포 빌드에서 잰 값 (2026-11-01)

위의 수치는 전부 데스크톱(`FT.Sim`)입니다. 실제로 사람이 겪는 곳은 브라우저라서,
`dotnet publish -c Release` 한 결과를 정적 서버에 올리고 크롬에서 다시 쟀습니다.

| | 데스크톱 | 배포 빌드(브라우저) |
|---|---|---|
| 세계 생성 | 102ms | **275ms** |
| 라운드 한 회 | 7.6ms | **73ms** |
| 저장 한 번 | 90ms | **175ms** (JSON 108 · gzip 62 · base64 1) |
| 세이브 읽기 + 첫 화면 | 130ms | **약 2초** (새로고침 → 저장된 판 복구까지) |

내려받기는 **5.15MB**(brotli, 파일 41개 · 전체 요청 48개)입니다. 비압축으로는 23.3MB 이고,
로컬 기준 빈 캐시에서 첫 화면까지 1.0초입니다. 처음 한 번만 받고 그 뒤로는 브라우저가 캐시합니다.

이 숫자는 **두 번의 맞교환**으로 정해졌습니다.

**트리밍을 켠다 — 8.0MB → 2.8MB.** 예전 `FT.App.csproj` 는 "트리밍이 모델 타입을 지우면
세이브가 깨진다"는 이유로 꺼 두었는데, 그 사이 `SaveGame.Options` 가 소스 생성 리졸버
(`SaveJsonContext`)를 **먼저** 쓰도록 바뀌어 전제가 사라졌습니다. 안전은 운에 맡기지 않고
`TrimmerRootAssembly` 로 모델 타입이 모여 있는 FT.Core 를 통째로 남깁니다. 남겨도 크기는
그대로이고(줄어드는 양은 거의 전부 BCL 쪽입니다), 덤으로 `SaveGame.cs` 의 IL2026 경고
다섯 개가 사라집니다. 모델 타입을 FT.Core 밖으로 옮기게 되면 이 뿌리도 같이 옮기세요.

**AOT 를 켠다 — 2.8MB → 5.15MB, 대신 CPU 3.7배.** 브라우저의 기본 런타임은 IL 을
해석해서 돕니다. 이 게임은 저장 한 번에 멤버를 수십만 번 쓰므로 그 해석 비용이 그대로
기다리는 시간이 됩니다. 미리 컴파일하니 저장의 JSON 쓰기가 350 → 108ms, 라운드가
150 → 73ms 가 됐습니다. 한 번 받고 몇 시간을 노는 게임이라 내려받기 쪽을 내줬습니다.
`dotnet workload install wasm-tools` 가 필요하고, **배포 빌드가 40초에서 20분쯤으로**
길어집니다 — CI 를 붙일 때 염두에 두세요. 개발(`dotnet run`)에는 영향이 없습니다.

### 세이브를 쪼개 보고 선수를 접었습니다 (2026-11-01)

배포본에서 저장 한 번이 560ms 였습니다. 쪼개 보니 답이 하나로 나왔습니다.

```
JSON 490ms · gzip 70ms · base64 5ms
  └ 선수 6,000명  3,564KB  396ms   ← 전체의 81%
    구단   240개    574KB   89ms
    리그    12개    353KB   32ms
```

**추측이 두 번 빗나갔습니다.** 압축이 범인인 줄 알고 브라우저 기본 `CompressionStream`
으로 바꿀 생각을 했는데 gzip 은 70ms 였습니다(네이티브 zlib 이라 이미 빠릅니다).
base64 를 빼고 IndexedDB 에 바이트로 넣을 생각도 했는데 base64 는 5ms 였습니다.
둘 다 고쳤으면 한나절을 쓰고 아무것도 못 줄였을 것입니다.

선수 한 명이 594바이트였고 그중 **300바이트가 이름**이었습니다 — 능력치는 이미 배열이었지만
선수 자신은 객체라 `"internationalGoals"` 같은 이름 스물다섯 개를 6,000번 적고 있었습니다.
스태프를 접을 때 쓴 방법을 선수에게도 적용했습니다(`PlayerConverter`).

| | 전 | 후 | AOT 까지 켠 뒤 |
|---|---|---|---|
| 세이브 원본 | 4.48MB | **2.73MB** | 〃 |
| 압축 후 | 695KB | **610KB** | 〃 |
| 선수 한 명 | 594B | **321B** | 〃 |
| 전술 슬롯 하나 | 76B | **14B** | 〃 |
| JSON 쓰기(브라우저) | 490ms | **350ms** | **108ms** |

구단에서 가장 큰 것은 저장된 전술이고(2,403B 중 1,227B), 그중 840B 가 슬롯 열한 개였습니다.
슬롯 하나가 `{"slotIndex":1,"position":8,"role":{"role":8,"duty":1},"assignedPlayerId":17}` 인데
값은 숫자 다섯 개뿐입니다 — 240구단 × 11자리면 이름만 180KB 입니다(`FormationSlotConverter`).

**중첩 묶음은 변환기를 직접 부르세요.** 처음엔 능력치·계약·기록을 `JsonSerializer.Serialize`
로 다시 넘겼는데, 바이트는 46% 줄었는데 시간은 그대로였습니다. 선수마다 아홉 번씩,
6,000명이면 54,000번 타입 정보를 새로 뒤지고 있었습니다. 변환기를 한 번 찾아 들고 쓰니
그제야 시간이 따라 내려왔습니다. **바이트가 준다고 시간이 주는 것이 아닙니다.**

**뒤쪽 0 은 적지 않습니다.** `AttrJson.WriteArray` 가 꼬리의 0 을 자릅니다. 한 경기도
뛰지 않은 선수의 시즌·통산 기록(열두 자리씩)과 아무도 설정하지 않는 계약 뒷부분이
6,000명분 쌓여 있었습니다. 읽는 쪽이 모자란 자리를 0 으로 두므로 값은 같고,
예전 세이브도 그대로 읽힙니다.

측정은 `/perf` 에서 합니다 — 메뉴에 없고 주소를 직접 쳐야 들어오는 화면입니다.
저장을 세 번 재고 조각별로 쪼개 보여 줍니다.

### 데스크톱 수치도, 개발 서버 수치도 배포를 예측하지 못합니다

`dotnet run` 의 개발 서버에서 재면 **저장 한 번이 3.0초**로 나옵니다. 같은 릴리스 코드인데
배포본에서는 0.175초입니다 — 열일곱 배입니다. 개발 서버는 디버깅을 켠 채로 돌아
런타임 최적화가 빠지고, AOT 도 publish 할 때만 돕니다.
개발 서버에서 나온 "3초"를 보고 저장을 뜯어고치려 들면, 있지도 않은 병목을 쫓게 됩니다.
브라우저 수치는 **반드시 `publish` 한 결과로** 재세요.

재는 법도 한 가지 함정이 있습니다. 확장 도구로 버튼을 누르고 **다음 호출에서** 시간을 재면
왕복 시간에 묻혀 21ms 같은 가짜 값이 나옵니다. 한 번의 스크립트 안에서 `button.click()` 하고
`performance.now()` 차를 봐야 맞습니다 — 무거운 일은 그 `click()` 안에서 동기로 끝납니다.
